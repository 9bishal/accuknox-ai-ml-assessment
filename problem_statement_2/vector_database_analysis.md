# Vector Database Analysis

## 1. What is a Vector Database?

A vector database is a database designed to store, index, and search
high-dimensional numerical vectors.

These vectors are commonly generated by machine learning models called
embedding models. An embedding represents the semantic characteristics
of data such as text, images, audio, or other objects as a numerical
vector.

For example, a text such as:

"What is the company's leave policy?"

can be converted into a vector such as:

[0.12, -0.43, 0.71, 0.08, ...]

The exact values are not meaningful individually. Together, however,
the vector represents information about the semantic meaning of the
original text.

Texts with similar meanings tend to have vectors that are closer
together in the embedding space.

---

## 2. Why are Vector Databases Needed?

Traditional relational databases are very effective for structured
data and exact queries.

For example:

SELECT \* FROM employees
WHERE department = 'Engineering';

However, an application may need to answer semantic questions such as:

"How can I apply for work from home?"

A keyword-based search may fail to retrieve a document containing:

"Employees can request remote working arrangements through their
manager."

The words are different, but the meaning is similar.

Vector search addresses this problem by comparing the numerical
representations of the query and the stored documents.

---

## 3. How Vector Search Works

A typical vector search pipeline is:

User Query
↓
Embedding Model
↓
Query Vector
↓
Vector Similarity Search
↓
Top-K Similar Vectors
↓
Relevant Documents
↓
Application / LLM

For a document-based AI assistant, the documents are first processed:

Documents
↓
Text Extraction
↓
Chunking
↓
Embedding Generation
↓
Vector Database

When the user asks a question, the same embedding model converts the
question into a vector. The vector database then searches for stored
vectors that are closest to the query vector.

---

## 4. Similarity Measures

Several distance or similarity measures can be used for vector search.

### Cosine Similarity

Cosine similarity measures the angle between two vectors.

It is commonly used for text embeddings because it focuses on the
direction of the vectors rather than their magnitude.

The formula is:

cosine_similarity(A, B) =
(A · B) / (||A|| ||B||)

A value closer to 1 generally indicates that the vectors are more
similar in direction.

### Euclidean Distance

Euclidean distance measures the straight-line distance between two
vectors.

A smaller distance indicates that the vectors are closer together.

### Dot Product

The dot product can also be used to compare vectors and is commonly
supported by vector search systems.

The appropriate metric depends on the embedding model and how the
embeddings are generated.

---

## 5. Vector Indexing

Searching every vector one by one can become expensive when a database
contains millions of vectors.

Vector databases therefore use specialized indexing techniques to
make similarity search faster.

Common approaches include:

- HNSW (Hierarchical Navigable Small World)
- IVF (Inverted File Index)
- Product Quantization
- Approximate Nearest Neighbor (ANN) search

These techniques generally trade some degree of exactness for
significantly faster retrieval.

For many real-world RAG systems, approximate nearest-neighbor search
provides a useful balance between retrieval quality and latency.

---

## 6. Metadata

A vector should generally not be stored by itself.

For example, a document chunk might contain:

Vector:
[0.12, -0.43, 0.71, ...]

Metadata:

document_id: 123
department: engineering
document_type: security_policy
created_at: 2026-01-15
access_level: internal

Metadata enables filtering before or during retrieval.

For example:

"Search only documents belonging to the Engineering department."

This is particularly important in enterprise applications where users
may have different permissions.

---

## 7. Hybrid Search

Pure vector search is not always sufficient.

Some queries benefit from semantic search while others depend on exact
keywords.

For example:

"What is the error code CVE-2026-1234?"

An exact keyword search may be more useful than purely semantic
similarity.

Hybrid search combines:

- Keyword / lexical search
- Vector / semantic search

This can improve retrieval quality for systems containing technical
documentation, product names, identifiers, or other exact terms.

## 8. Comparison of Vector Database Options

For the hypothetical enterprise knowledge assistant, I would consider
the following technologies:

| Technology | Type                        | Strengths                                                                  | Limitations                                                                   |
| ---------- | --------------------------- | -------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| FAISS      | Vector search library       | Fast local similarity search, simple to prototype                          | Requires building additional database and application infrastructure          |
| pgvector   | PostgreSQL extension        | Combines relational and vector data in PostgreSQL                          | May require additional optimization for very large vector workloads           |
| Pinecone   | Managed vector database     | Fully managed, scalable, simple deployment                                 | Adds dependency on a dedicated managed service                                |
| Weaviate   | Vector database             | Vector search, metadata filtering, hybrid search and RAG-oriented features | Additional infrastructure compared with using an existing relational database |
| Milvus     | Open-source vector database | Designed for large-scale vector workloads                                  | More infrastructure and operational complexity                                |

---

## 9. FAISS

FAISS is a library developed for efficient similarity search over
dense vectors.

Its main advantage is simplicity and performance for local or
application-controlled workloads.

I would consider FAISS for:

- Prototypes
- Research
- Local RAG applications
- Offline vector search

However, FAISS by itself is not a complete database solution. An
application may need to implement persistence, metadata management,
access control, and other database functionality separately.

---

## 10. pgvector

pgvector is an extension that allows PostgreSQL to store and search
vector embeddings.

One major advantage is that structured application data and vector
embeddings can be managed in the same database.

For example:

Users
Documents
Permissions
Metadata
Embeddings

can all be represented within PostgreSQL.

This can significantly simplify an application where PostgreSQL is
already the primary database.

---

## 11. Pinecone

Pinecone is a managed vector database designed specifically for
similarity search applications.

Its managed nature can reduce the amount of infrastructure that an
engineering team needs to maintain.

It is particularly attractive when:

- Vector search is a core application requirement
- The team wants managed infrastructure
- The system needs to scale independently
- Operational simplicity is important

The trade-off is that it introduces an external managed dependency
instead of keeping vector search within an existing database.

---

## 12. Weaviate

Weaviate is a vector database designed around semantic search and
AI-oriented applications.

It supports vector search along with metadata filtering and hybrid
search.

This combination is useful for RAG applications because retrieval may
need to consider both semantic similarity and structured constraints.

For example:

"Find documents related to authentication that belong to the
Engineering department and are accessible to the current user."

This requires more than simply comparing vectors.

---

## 13. Milvus

Milvus is an open-source vector database designed for large-scale
vector search.

It is suitable for applications where vector retrieval is a major
component and the system needs to handle large numbers of embeddings.

Its flexibility and scalability are strengths, although operating a
dedicated vector infrastructure can introduce additional operational
complexity.

---

## 14. Recommended Choice

### Hypothetical Problem

Assume I am building an enterprise knowledge assistant for an
organization with several thousand internal documents.

The documents include:

- HR policies
- Technical documentation
- Security guidelines
- Product documentation
- Internal FAQs
- Engineering documentation

Employees should be able to ask natural-language questions and receive
answers based on the organization's internal knowledge.

The system should support:

- Semantic search
- Metadata filtering
- Hybrid search
- RAG
- Document-level access control
- Future scalability

### Selected Database: Weaviate

For this particular problem, I would choose Weaviate.

The primary reason is that retrieval is a central component of the
application, and the system needs more than basic vector similarity
search.

The combination of vector search, metadata filtering, and hybrid
retrieval makes it a suitable fit for an enterprise RAG architecture.

For example, when an employee asks:

"What is the process for requesting production access?"

the system could:

1. Convert the question into an embedding.
2. Perform semantic search against technical and security documents.
3. Apply metadata filters based on document type and user permissions.
4. Optionally combine semantic search with keyword matching.
5. Retrieve the most relevant document chunks.
6. Provide those chunks as context to the LLM.
7. Generate the final answer.

---

## 15. Why Not Simply Use PostgreSQL?

PostgreSQL with pgvector would also be a strong option.

If the application already depends heavily on PostgreSQL and the vector
search workload is relatively moderate, pgvector could be the better
engineering decision because it reduces infrastructure complexity.

For example:

PostgreSQL
├── Users
├── Documents
├── Permissions
├── Conversations
└── Embeddings

This can be simpler to operate than maintaining both PostgreSQL and a
separate vector database.

However, for the hypothetical problem in this assessment, I would
choose Weaviate because semantic retrieval and hybrid search are
central requirements rather than secondary features.

---

## 16. Trade-offs

The decision is not based on one database being universally better.

| Requirement                                | Weaviate                 | pgvector  |
| ------------------------------------------ | ------------------------ | --------- |
| Vector search                              | Strong                   | Strong    |
| Metadata filtering                         | Strong                   | Strong    |
| Hybrid search                              | Strong                   | Available |
| Existing PostgreSQL integration            | Requires separate system | Excellent |
| Operational simplicity with PostgreSQL app | Lower                    | Higher    |
| Dedicated vector infrastructure            | Yes                      | No        |
| Suitable for RAG                           | Yes                      | Yes       |

Therefore, my choice would depend on the application context.

For a vector-centric RAG platform, I would lean toward Weaviate.

For an application that already has PostgreSQL as its primary data
store and has moderate vector-search requirements, I would strongly
consider pgvector.

---

## 17. Conclusion

Vector databases are an important component of modern AI applications
because they allow systems to retrieve information based on semantic
similarity rather than relying only on exact keyword matching.

For an LLM-based enterprise knowledge assistant, a vector database can
act as the retrieval layer in a Retrieval-Augmented Generation
architecture.

For the hypothetical system considered here, I would select Weaviate
because of its combination of vector search, metadata filtering, and
hybrid retrieval capabilities.

However, I would not treat this as a universal choice. The final
decision should consider factors such as dataset size, latency
requirements, infrastructure constraints, existing databases,
security requirements, operational complexity, and cost.
